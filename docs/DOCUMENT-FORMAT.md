# Recursive project format

The desktop editor reads versions 1–15 and saves version 15. Version 15 adds retained image assets through an optional `trashed` flag and content-free `removed_assets` identities for permanent removal, preserving consumer references while excluding unavailable artwork from live lookup. Version 14 adds five horizontal-rule styles and preserves earlier line frames, centered strokes and default ink through a hidden compatibility property. Version 13 adds editable arrow geometry and preserves earlier horizontal placement and single right heads through a size-relative fallback, including component size overrides. Version 12 corrects the new on/off switch default to on; migration materializes the previous off default in older sparse switches, including grouped, alternate, retained and component content. Explicit states and instance overrides retain precedence. Version 11 adds per-page and per-alternate review discussions. Version 10 adds known removed page destinations. Version 9 adds retained component libraries. Version 8 adds persisted library import correspondence. Version 7 makes source root crop/markup shared and adds explicit root appearance overrides. Version 6 adds component libraries, source ownership and separate library/source notes. Version 5 adds retained pages through an optional `trashed` flag. Version 4 adds durable instance-local lock overrides and separates source editing locks from instance state. The recursive project remains authoritative; derived renderer views are never saved. Version 3 adds independent alternate notes and explicit shared named-version identities. Older readers reject this version rather than silently dropping those relationships.

A project owns pages, named versions, component definitions, component libraries, binary assets and contextual settings. Each page has a stable ID, notes, an optional parent and independent alternate content. An alternate owns its notes and optionally references a named version; its retained label must match that name. A page may have at most one alternate in each named version. Content stores ordered recursive nodes. IDs are unique among siblings; a node path, scoped to page/version/definition, identifies descendants. Resource IDs are unique across pages, alternates, named versions, assets, definitions and libraries. The allocator advances above all stored IDs.

Version-2 migration preserves alternate IDs, labels and content without inferring shared identity from equal labels. Each legacy alternate receives a copy of its owner's notes, preserving the prior displayed/exported notes. Its named-version reference remains absent until an explicit operation establishes a relationship. Navigation preferences are separate from the document. Migration reads without modifying the input and subsequent saves use version 15.

A node has a local origin, lock/markup flags, optional normalized crop and sparse typed properties. Its content is a leaf control with requested dimensions, a group of children or a component reference with descendant overrides. Automatic dimensions are represented explicitly and never confused with measured layout. Derived bounds, rendering caches and selection are not persisted.

Component expansion applies inner content overrides before outer overrides. Editing locks are cleared when crossing each definition boundary; the current owning instance then applies its own optional Boolean `patch.locked` values. Source node locks stay intact in source workspaces. Missing lock overrides mean unlocked instance children. Version-3 migration changes the version only, preserving canonical content and source locks without inventing local locks from former inherited behavior. Reset removes the sparse override; source edits then propagate. Expansion returns an owned group that can be retained independently of the source. Obsolete paths produce diagnostics without applying their values to a different node. Cycles are errors. Missing definition IDs remain valid dangling references and are reserved below next_id; zero IDs or references colliding with another resource type are invalid. Resolution produces a disposable150×150 placeholder with crop cleared, without changing the canonical instance or its overrides. Overrides under the missing source are reported as orphaned. Expansion has a control-count budget; validation checks hierarchy depth independently of definition order.

Version-1 migration retains all existing properties, geometry, IDs, groups, links and text. Group children become parent-local. When old logical groups interleave in drawing order, an explicit structural paint-path order preserves their original layering; ordinary recursive order remains the default. Component instances are atomic paint paths; layout maps expanded descendants to their instance ordering position. Migration does not write its input. Component definitions currently reject this legacy ordering extension; converting such a selection to a component needs an explicit normalization operation in the editor.

Validation bounds file size, asset bytes, hierarchy depth, node count and text sizes. It rejects invalid coordinates, dimensions, crops, IDs, parent cycles and resource references. Known catalog property types and states are checked during validation. Specialized schemas remain incomplete; unknown fields are preserved.

ProjectStore reads all fifteen formats and writes version 15 using the existing atomic file replacement path. Encoding/validation occurs before any file replacement. A failed validation therefore preserves the previous file. The desktop app uses ProjectRepository/ProjectStore for saves and recovery, retaining exclusive recovery ownership.

## Verification

Ten document tests cover migration, recursive geometry, expansion/overrides, assets/alternates, validation and failure preservation. See SESSION-SPEC.md for the current full-suite count, including recursive workspace and live app workflow checks. Clippy passes with warnings denied.

The read-only check_migration example passed against five saved native test documents, including the live editor's derived controls. It verifies order, geometry, text, round trips and unchanged source bytes. A native macOS nested-edit/save/close/reopen check also passed; see RECURSIVE-EDITOR.md. Full rendering fidelity and other-platform runtime checks remain open.

Empty existing definitions resolve to real empty groups with disposable component-label metadata; canonical instances and overrides remain unchanged. Empty groups measure150×150 and count as visible paint units. Detach/copy remove derived component metadata. Old explicit orders that omit only empty groups remain valid, with those placeholders appended to effective drawing order without file mutation. Other missing paths remain invalid. First/last-child edits replace the empty-group paint unit in place. Empty document roots are not group nodes and remain blank.

New ID allocation skips identities still present in component override paths across pages, alternates and definitions. This preserves orphaned child identities even when an imported path is above the stored allocator; loading itself does not rewrite the document.


List `row_links` uses the additive typed property value `{ "type": "links", "value": [null, {"type":"page","value":2}, {"type":"back"}] }`. Header is row0 when enabled. At most10,001 nullable targets are accepted; URLs must use HTTP(S), have no control characters and stay within10,000 bytes. Page references are validated against project pages. Deletion/cross-document paste remove unavailable targets throughout nodes, groups, component definitions and local override properties. Earlier v2 projects need no migration. Older readers that do not know the new value variant cannot load files containing it.

List `row_icons` uses `{ "type": "icons", "value": [null, {"source":"catalog","id":"camera-solid"}] }`. Header is row0. Up to10,001 nullable entries are accepted; each nonempty ID is at most128 ASCII alphanumeric, hyphen or underscore bytes. Valid unknown IDs are retained for forward catalog compatibility and render a placeholder. This additive v2 value needs no migration for earlier files; older readers cannot load documents containing the new variant. Component override properties use the same representation. Paths, raster caches and picker state are never stored in the project.

Custom row icons use `{ "source": "asset", "id": 8 }` in the same nullable icon array. The ID must refer to an existing embedded asset and must be nonzero. Asset bytes are stored once and remain unchanged by tinting. Clipboard transfer collects and remaps these references in ordinary controls, component definitions and local overrides. Replacing a shared asset updates every user of that ID; undo restores both bytes and assignments. This additive variant is not readable by earlier binaries.


Button and Dropdown `icon` use `{ "type": "icon", "value": { "source": "catalog", "id": "arrow-right-solid" } }`, or an asset source as above. Explicit `null` values clear inherited icons. Separate choice properties `icon_size` and `icon_rotation` store16/24/32/48/64/128 and0/90/180/270 respectively. A Button's `menu_icon` boolean is independent of its optional icon. These additive v2 properties share validation, component patches and clipboard asset remapping; older binaries cannot read the new `icon` value variant. Rotation/tint caches are derived and never rewrite embedded source bytes.


Standalone `icon` and `icon_label` control kinds reuse the single `icon`, `icon_size` and `icon_rotation` properties. `icon_label` adds `label_position` choices bottom/left/right; both have border choices none/solid. Icon size is always derived, and icon-label height is always derived even when an incoming file has a fixed requested height. Width-only resizing follows the catalog. Empty sources use24/48-unit fallbacks respectively. No new format version or copied artwork is required.


The `circle_button` kind supports both fixed and automatic dimensions; each automatic dimension resolves to48. It reuses nullable `icon`, `icon_size`, `icon_rotation`, `label_position` and `border`, plus fill, text and state. New insertion explicitly stores `plus-solid`; absent or null icon data stays empty when loading existing nodes. Native circles use the shared styled ellipse in canvas and exports. This adds no new serialized format version.

The `pointed_button` kind resizes horizontally and calculates automatic height from text, icon and menu sizes with a27-unit minimum. Stored fixed heights are respected. `direction` accepts left/center/right; `border` accepts none/solid. New insertion stores left/none explicitly; unset values resolve to right/solid. Optional icons use the shared typed source/size/rotation properties. A `menu_icon` boolean adds an independent down arrow. State supports normal/disabled. Whole-control links are active; label markup does not create inline hotspots.

The `multiline_button` kind splits the first literal newline into title and secondary rich text. Its secondary font is70% rounded up, with a minimum8. Automatic width follows the title and optional icon, with a16-unit addition; automatic height wraps the secondary text against the title plus style padding. Fixed dimensions are stored unchanged. `background_opacity` affects only the fill; text contrast switches at75% opacity on dark fills. The existing typed icon, size and rotation fields apply. Whole-control and inline links coexist, with inline hits taking precedence.

The `button_bar` kind uses literal commas to separate segments; embedded newlines stay within a segment. Both dimensions accept fixed or automatic sizing. `selected_index` defaults to0, with−1 for no selection, and `row_links` stores per-segment page, Back or URL targets. Narrow bars omit whole segments without discarding stored selection or targets. Single-item text adds a visual ellipsis segment without adding a link-editor entry. Text edits match trimmed labels in occurrence order for links; renamed labels retain their position when the count stays unchanged. This reuses existing typed values and does not change the format version.

## Rectangle appearance

Rectangle reuses typed choice `border` values `solid`, `rounded`, `dashed`, `dotted` and `none`, color `border_color`, and numeric `background_opacity` in the range 0–1. Missing values mean a square outline, style-dependent ink and opaque fill. `dotted` is a legacy alias for dashed rendering. Existing rectangle text and shape properties are retained. These additive properties require no format migration; component overrides use the same representation. See OUTLINES.md.

## Project palette

`settings.palette` optionally holds opaque RGB byte arrays named `selection` and `link`. Missing values retain the built-in defaults: `[149,188,242]` and `[8,83,148]`. The entire field is omitted when both colors are default, keeping legacy project serialization stable. Invalid array lengths and values outside 0–255 are rejected during decoding. Per-control colors remain node properties; derived render hints are never saved.

Palette changes belong to document history and apply across pages, alternate versions and components. Local defaults for newly created projects are stored separately from document history; opening an existing project does not substitute these defaults. See PROJECT-COLORS.md.

## Retained pages (version 5)

`pages` remains the canonical ordered resource sequence. A page with `trashed: true` retains its ID, position, parent, official content/notes and every alternate. False is the default and is omitted on serialization. A migration from versions 1–4 makes all pages live without changing identity, content or order. Older format tags containing true trash flags are rejected; the flag must not silently pass through a reader that does not support retained state.

`Project::live_pages`, `live_page`, `first_live_page` and `live_parent` define the navigation boundary. Official and alternate surface lookup excludes retained pages. A live page whose stored parent is retained appears at the root; loading does not erase that parent reference. Navigation, page edits, link-target pickers, site-map generation, presentation history and export selection use live pages. Existing links to retained identities remain stored and valid; attempting navigation to an unavailable page cannot change current selection.

Validation and ID allocation still visit every page and alternate. Shared named-version renames and pruning include retained memberships. Assets/definitions are not collected when their page is hidden. The project requires 1–1000 live pages and allows up to1000 retained pages; the existing combined50000-node,64MB file and32MB embedded-asset budgets still apply to the whole document. Parent cycles, missing identities, invalid properties/coordinates and resource collisions are rejected across both sets.

Recovery translates canonical clean baselines for older documents before comparing current content; the omitted false flag preserves historical field order. Loading/migration does not overwrite the named file or recovery record. Retained contents survive recovery restart and named save. This is the persistence boundary; user-facing Trash/Restore operations and their specific history behavior are still being implemented. Existing immediate Delete remains distinct.

## Component libraries (version 6)

Each library stores a resource ID, name, notes, editable Content and source ownership records. A source record identifies one canonical definition and one top-level placement node, plus independent source notes. Every definition has exactly one owner. The placement is an instance referring to that definition, without local overrides or ordinary properties. In version 7 its crop and markup are canonical shared source appearance. Ordinary library controls and instances are valid but do not become sources without an ownership record. `default_library` optionally identifies the destination for page-to-component conversion.

Versions 2–5 gain a default library only when definitions exist. Migration preserves all definition, node, instance and override identities and allocates fresh library/placement IDs above the validated old allocator. Placements use a deterministic layout starting at four columns because older files did not contain library positions. Large source collections widen the grid while keeping all positions within the coordinate limits. Existing page and source artwork is unchanged. Version 1 has no reusable definitions. Input files remain untouched until an explicit save. Older format tags carrying nonempty library data are rejected.

Library resources participate in ID collision checks. Ordinary library controls participate in the existing node, depth, asset, link and dependency checks. Canonical source placements are metadata wrappers: they do not count source content twice against the node budget or add a dependency level. Library and source notes each allow up to one million UTF-8 bytes; at most 1000 libraries are accepted. Empty libraries and empty sources are valid.

Control clipboard transfer includes only the libraries' required source placements and notes, excluding unrelated ordinary controls. Cross-project transfer remaps resource and placement IDs; same-project reuse retains current ownership. Legacy clipboard data gains default ownership. Invalid clipboard operations restore the complete pre-paste document and selection. Source deletion removes its ownership/placement while keeping ordinary missing instances and supporting Undo. Recovery recognizes old clean fingerprints before migration and preserves unsaved-change status.

The model and persistence layer precede dedicated library/source navigation. Library creation, lifecycle, selection and editing UI remain separate implementation work.

## Shared source appearance (version 7)

The unique owning source placement stores shared crop and markup; Definition content stores the full editable children. Library and ordinary instance views apply the shared root appearance. Source-focused editing displays the full child content. Source editing locks remain independent from instance editing locks.

An ordinary instance can carry an empty-path override with only `crop` and `markup`. Absent fields inherit; crop Clear and markup false explicitly clear shared values. Region specifies a local crop. Root position, size, locks and ordinary properties are forbidden in that patch. Nonempty descendant paths retain their existing meaning and additionally support markup overrides. Legacy node-level crop/markup remain readable; root patches take precedence. New root edits use patches, and whole-instance reset clears patches and legacy root appearance without moving the instance. Empty-source fallback ignores crop during rendering while retaining canonical values.

Versions 1–6 migrate without changing input files. Older tags cannot carry shared source crop, empty-path patches or markup patches. Version6 source markup previously affected only the library view; migration adds explicit false root overrides where needed to preserve ordinary instances' prior appearance. Clean recovery baselines are translated using old canonical serialization, including version6. Copy reuse compares shared appearance as well as child definitions, preserving frozen clipboard contents when a source changes. Conversion moves group crop/markup to its source placement and removes unsupported group properties from the replacement instance.

## Group metadata and source structural actions

Ordinary groups can retain `group_name` and `group_notes` typed Text properties when source placements become nested content. Names allow10000 bytes and notes1000000 bytes; non-text values for these keys on groups are invalid. This extends the current unreleased version7 contract. Empty metadata is valid. The ordinary source ownership wrapper still has no free properties: promotion transfers this metadata into Definition.name and ComponentSource.notes, then removes it from the placement.

Library Group materializes owning wrappers as ordinary canonical groups without expanding nested ordinary instances, removes the old active definitions/ownership and promotes the new outer group. External references retain the old IDs and become missing. Ungroup allocates fresh root node/source identities for promoted children; it is not an identity restoration. Undo restores the original graph and allocator snapshot. Source duplication preserves scoped child IDs/content/locks, name, notes and appearance, but allocates fresh source and placement IDs. Existing instances continue to refer to the original source. Page-group conversion also carries retained group notes into its new source.

## Library import correspondence (version 8)

An optional `imports` list on each library records an originating project string, originating library ID and a map from foreign definition IDs to local definition IDs, including retained missing dependency references where necessary. Empty lists are omitted. Different libraries can retain the same foreign origin after independent copies; origin equality alone must never collapse explicit resources. Definition bindings may outlive a deleted source. Their local IDs remain reserved below `next_id`, and allocation skips retained bindings. A binding cannot refer to a different live resource type.

Origin strings must be nonempty, at most512 bytes and contain no control characters. Origin/library pairs are unique within a library. Foreign library/definition IDs and local target IDs are nonzero; targets are distinct within each record. The project allows at most1000 correspondence records and50,000 definition bindings in total. A planner must check current ownership before reusing a historical binding; schema validation does not establish that a target still belongs to the receiving library.

Versions1–7 migrate without correspondence. Nonempty or malformed correspondence under an older version tag is rejected. Version7 migration retains artwork, IDs, ownership, appearances and allocator state. Recovery translates a proven clean version7 content fingerprint to the current format in memory while preserving raw named and recovery files; dirty copies remain dirty. New correspondence survives local checkpoints, recovery and named save/reopen. The import planner uses these bindings for reuse, replacement and missing-source restoration. Navigator resource Paste uses the planner and atomic application path.

## Retained component libraries (version 9)

An optional library `trashed` boolean defaults to false and is omitted when false. True retains the complete library and its owned definitions, notes, source placements, crop, locks, provenance and assets. Physical ownership, graph validation and identity reservation include retained libraries. Active editing, catalogs and normal instance resolution exclude their sources. Saved consumers retain their references and overrides and resolve as missing until restoration. A separate read-only preview can expose retained artwork without changing storage or normal availability.

Versions1–8 migrate with live libraries. A true or malformed retained flag under an older version tag is rejected. Recovery migrates clean version8 fingerprints in memory without altering raw named/recovery files; unsaved changes stay dirty. Zero live libraries is valid. New unowned definitions receive a live default library rather than being assigned to a retained default. Cut removes only requested libraries and owned definitions in one undoable operation; dependency-only clipboard resources and assets remain. Shared Trash uses typed page/library selection and atomic restoration while preserving page-adoption history. Application clipboard publication-before-Cut remains separate integration work.


## Removed page destinations (version 10)

The optional `removed_pages` set records IDs of permanently removed pages, without their names, notes, controls or alternate content. Empty sets are omitted. IDs are nonzero, distinct from all current resource IDs and below `next_id`; at most 50,000 are accepted. Ordinary scalar, row and override page links may reference either a stored page or a recorded removed destination. Arbitrary missing targets remain invalid. A recorded target displays Broken and cannot be navigated to.

Readers migrate versions 1–9 without inventing removed destinations. A file claiming an earlier version while carrying a nonempty removed set is rejected. Working-copy migration preserves old clean/dirty fingerprints and does not rewrite the source file during reading. Permanent page removal and its history handling are described in PERMANENT-REMOVAL.md. This schema does not define deliberate clipboard reconnection of removed pages.

## Review discussions (version 11)

The optional `reviews` map associates a page/alternate resource ID with its discussion, including retained pages. Each discussion has scoped comment IDs, a monotonic comment allocator and a separate monotonic marker allocator. Comments store their parent, author identity/display name, created/edited times, revision, imported/deleted status, read/like identity sets and text/owned callouts. Review identity namespaces are separate from artwork IDs. Whole-surface import preserves parent/marker relationships and remaps typed `surface:` links using final resource decisions. Marker links use `callout:` targets. Only parsed link targets are rewritten; escaped markup, formatting and external links are preserved.

Validation enforces ownership, at most 10,000 comments across the project, bounded text/marker counts, bounded acyclic threads, finite marker positions and valid reserved link identities. Deleted comments have empty bodies; their restoration data and drafts are session-only. Older formats cannot contain nonempty review data. Version-10 named files and working copies migrate through the same document boundary; migration does not rewrite the original file or change a previously clean recovery baseline.

Review commands use normal project persistence but do not create drawing Undo entries. Artwork-only history preserves current review state. Replaying resource/import changes refuses to remove or overwrite later feedback. Import/discard history is otherwise reversible. Explicit permanent page removal also removes its discussions from all retained drawing snapshots.

## Retained images (version 15)

Each asset may contain `trashed: true`. False is the default and is omitted. Validation and ID reservation include retained assets; live image lookup excludes them. Controls, component overrides and transfer payloads keep their references and encoded bytes, so restoring the asset restores availability without rewriting its consumers. Older format tags containing true retention flags are rejected. Migration of versions 1–14 preserves canonical clean recovery fingerprints in memory and leaves original files untouched. See the [asset lifecycle contract](ASSET-CATALOG.md) for current integration limits.

An optional `removed_assets` set reserves permanently removed image IDs without their name, media metadata or bytes. It is omitted when empty and bounded to 50,000 entries. IDs must be nonzero, below the allocator, and disjoint from live/retained resources and removed page IDs. Image/icon/row-icon references may point to these markers; asset import correspondence still requires an actual asset record. Old version tags containing removed-image identities are rejected. Permanent removal sanitizes pending and historical document projections; saved consumers remain broken references rather than being rewritten or captured by new resources. Transfer envelopes carry/remap these identities with their dependent controls.
