# Icon rendering

Catalog icons use their actual physical scale and fractional position, with one texel per display pixel while the complete raster fits the allowance below. Quarter turns are applied during rasterization. Raster bounds enclose the nominal control and all Bezier control points. Including those points prevents the rasterizer from changing curve subdivision through its clipping path. This is separate from avoiding texture upscaling.

The painter uses the existing licensed artwork. Saved icon sizes, control layout, insertion behavior, SVG/PDF export geometry and project fonts are unchanged. Custom image icons retain their separate image path. Normalized paths and their control-point bounds are computed once per catalog icon and reused on cache misses. The complete catalog has 1,595,427 bytes of point/verb payload, excluding allocation and object overhead. Initialization is lazy; no extra path raster is retained.

Texture caching includes scale, fractional phase and rotation, with an LRU limit of 128 entries and 16 MiB of accounted texture pixels. Integer-pixel panning and color changes reuse textures, including the new large-icon cases. Fractional panning creates new rasters; broad document performance remains to be measured. These budgets do not bound total application memory.

Complete raster rectangles are limited to 2,048 pixels per side, including padding. A single maximum rectangle occupies 16 MiB. Beyond that allowance the prior 512-pixel filtered fallback remains; no universal one-to-one claim applies to arbitrary display density or geometry. Separate tile rasterization is not used because clipping curves independently changed their coverage.

Verification includes six simulated display densities through 5, seven sizes including a 128-point icon at maximum 300% zoom, and four rotations. Whole-canvas exported-path comparisons cover large nonsquare controls, fractional positions and clipping. Integer-pixel pan/color reuse, cache eviction, invalid geometry and extreme-size fallback are also checked. All 303 selected checks and warnings-denied all-target Clippy pass. Reuse additionally matches the prior SVG renderer exactly in 256 regression cases, and all 2,060 catalog entries have supported geometry.

Native macOS framebuffer comparisons at density 2 match complete-vector references in four large samples and direct rasterization in twelve ordinary samples. The old large-icon path differs by thousands of pixels in a side-by-side diagnostic. These are checks of the actual public painter, not full-application or native Windows/Linux acceptance, and do not resolve every reported source of canvas softness.

The optimized macOS ARM64 application before parsed-path reuse was reviewed with four 128-point icons at 300% zoom, fractional positions and quarter turns, plus a 21-control gallery and landing, desktop/phone contact and tablet-order sketches. A saved one-point move changes only the intended coordinate; Undo restores the fixture, and a fresh process reopens and resaves the edited position without altering other data. All 24 native/artifact checks pass. The candidate is closed and prior profile/recovery entries are preserved. These are scoped self-review results; no current Windows/Linux runtime, complete visual fidelity, performance or release acceptance is implied.

Optimized headless macOS profiling at density 2 covers 100 ordinary 24-point icons, 100 46-point icons, 36 128-point icons and four 384-point icons. Three runs use a deterministic catalog sample and 64 warm-up frames followed by 128 measured frames per case. Stationary/whole-pixel movement queues no texture updates after warm-up; fractional movement rebuilds each visible icon. Fractional median CPU costs are approximately 4.7, 7.4, 6.8 and 2.3 ms respectively, and texture data queued per frame ranges from 1.0 to 9.3 MiB. This measures the painter and egui frame work on an M1 Max, excluding GPU upload, native input and the rest of the app. It identifies repeated raster work as an optimization target without establishing smooth native frame cadence. Pixel accuracy must be preserved when reducing that work.

Parsed-path reuse matches the prior painter byte-for-byte in 3,328 additional sampled size/rotation/phase comparisons. Three paired runs of the identical optimized headless workload reduce fractional-motion median CPU time from 4.71 to 3.36 ms (100 24-point icons), 7.40 to 6.06 ms (100 46-point icons), 6.78 to 6.33 ms (36 128-point icons), and 2.32 to 2.24 ms (four 384-point icons). Texture-update counts and bytes are unchanged. These measurements establish reduced CPU work, not native frame cadence or GPU improvements. The current candidate now includes full application and Linux library/application/integration checks plus Linux/Windows lint and linking; see [platform validation](PACKAGING.md). Native desktop, physical cadence, final package and complete fidelity acceptance remain open. These source checks do not extend the earlier native visual observations to a new platform.
