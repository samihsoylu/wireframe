# Background project sessions

`ProjectSession` joins the working-copy store and revision coordinator behind one I/O thread. The desktop UI has not adopted it yet. Callers submit immutable document snapshots and consume ordered events; local checkpoints, named writes, retry timing and file ownership stay with the worker.

Ordinary edits checkpoint after a one-second quiet interval. A durable local revision starts the coordinator's five-second named-save delay when automatic mode is enabled. Turning automatic mode on checkpoints pending edits and makes them immediately eligible for a named save. Manual mode retains local edits without automatically updating the named file. Local write failures retry after five seconds; named writes use the coordinator's single retry after one second. Repeated background problems are deduplicated. Processed explicit requests receive their own result; unexpected worker termination is reported separately when polling events.

An unprocessed update is replaced by a newer snapshot, preventing ordinary rapid edits from accumulating full documents while I/O is slow. Flush, Save As and mode changes seal the current update mailbox. Later edits use a new mailbox, so coalescing cannot move them before an explicit save request. A test holds the worker, submits 200 changes across a save boundary, verifies only the two required snapshots remain, then confirms the named file contains the captured first snapshot while the local record contains the later one.

`flush` and `save_as` return request IDs. `Saved` events acknowledge their captured snapshot and path; `RequestFinished` resolves the corresponding request. The editor's `mark_saved_snapshot` updates that baseline without changing the current document, selection or history. Applying a save completion must never call `mark_saved` on a newer current document. Ended failed requests are removed from the coordinator so later manual edits do not silently restart them.

Save As reserves the selected destination's working-copy lock before any named write. Existing destination working records are preserved in unique archives. The source remains owned and durable until the destination write and acknowledgement succeed. Only then does the worker adopt the destination and remove the previous source working record. Failure keeps the source and any prepared destination recovery record. A destination modified after reservation is a conflict; another live owner blocks the operation. Selecting the current destination uses a normal guarded flush. Replacing an externally changed current destination still requires explicit conflict-resolution UI; this API does not bypass that guard.

A new-file reservation stores an explicit absent baseline. Existing fingerprint arrays remain readable. Missing fingerprint fields are invalid metadata, not an implicit reservation. This distinction prevents malformed records from being treated as permission to create a missing file. Save As can replace an unreadable explicitly selected destination, while unknown future local-record versions are retained unchanged.

`finish` drains queued updates, checkpoints the latest local document and releases ownership. It does not request a named flush. Manual application quit can use that path; automatic close must first await its flush request. `discard` explicitly removes the local record and prevents shutdown from recreating it. Failed finish/discard results must be surfaced while keeping the UI's document available. Dropping a session joins its worker, but callers that need error handling should call `finish` explicitly.

The UI must process events in order, correlate pending actions by request ID, keep Save As path changes tied to successful acknowledgement, and prevent edits during final close or refresh the close target afterward. Worker wake callbacks may request a repaint. File I/O can still block on the OS; a blocked filesystem operation also delays worker shutdown. This is not a cancellation or power-loss guarantee.

Checks cover real timers and file I/O, Save As ownership/failure, manual retention, automatic mode switching, immutable acknowledgements with editor Undo/Redo, discard, failed manual requests and bounded pending snapshots. The running desktop bundle remains on its earlier recovery flow. Pending work is actual UI routing, persisted mode settings, legacy recovery migration, candidate selection/archive restoration, status/error presentation and native close/restart acceptance on each platform.
