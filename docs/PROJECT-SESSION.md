# Background project sessions

`ProjectSession` joins the working-copy store and revision coordinator behind one I/O thread. The desktop app routes document edits and save controls through it. Callers submit immutable document snapshots and consume ordered events; local checkpoints, named writes, retry timing and file ownership stay with the worker.

Ordinary edits checkpoint after a one-second quiet interval. A durable local revision starts the coordinator's five-second named-save delay when automatic mode is enabled. Turning automatic mode on checkpoints pending edits and makes them immediately eligible for a named save. Manual mode retains local edits without automatically updating the named file. Local write failures retry after five seconds; named writes use the coordinator's single retry after one second. Repeated background problems are deduplicated. Processed explicit requests receive their own result; unexpected worker termination is reported separately when polling events.

An unprocessed update is replaced by a newer snapshot, preventing ordinary rapid edits from accumulating full documents while I/O is slow. Flush, Save As and mode changes seal the current update mailbox. Later edits use a new mailbox, so coalescing cannot move them before an explicit save request. A test holds the worker, submits 200 changes across a save boundary, verifies only the two required snapshots remain, then confirms the named file contains the captured first snapshot while the local record contains the later one.

`flush` and `save_as` return request IDs. `Saved` events acknowledge their captured snapshot and path; `RequestFinished` resolves the corresponding request. The editor's `mark_saved_snapshot` updates that baseline without changing the current document, selection or history. Applying a save completion must never call `mark_saved` on a newer current document. Ended failed requests are removed from the coordinator so later manual edits do not silently restart them.

Save As reserves the selected destination's working-copy lock before any named write. Existing destination working records are preserved in unique archives. The source remains owned and durable until the destination write and acknowledgement succeed. After a different destination is successfully written, automatic mode also saves the captured revision to the original named file before releasing it. Manual mode leaves the original unchanged. An original-file conflict, missing path or write failure does not invalidate the saved new copy: normal conflict protection remains in force and the successful receipt carries a visible warning. A rejected destination does not force an original-file write. Later queued edits remain local to the adopted destination. Only then does the worker adopt the destination and remove the previous source working record. Failure keeps the source and any prepared destination recovery record. A destination modified after reservation is a conflict; another live owner blocks the operation. Selecting the current destination explicitly through Save As captures its present baseline once, allowing intentional replacement or recreation. Retries retain that captured baseline. Ordinary Save and automatic writes still reject outside changes; even a clean flush checks the file.

A new-file reservation stores an explicit absent baseline. Existing fingerprint arrays remain readable. Missing fingerprint fields are invalid metadata, not an implicit reservation. This distinction prevents malformed records from being treated as permission to create a missing file. Save As can replace an unreadable explicitly selected destination, while unknown future local-record versions are retained unchanged.

`finish` drains queued updates, checkpoints the latest local document and releases ownership. It does not request a named flush. Manual application quit can use that path; automatic close must first await its flush request. `discard` explicitly removes the local record and prevents shutdown from recreating it. Failed finish/discard results must be surfaced while keeping the UI's document available. Dropping a session joins its worker, but callers that need error handling should call `finish` explicitly.

The UI must process events in order, correlate pending actions by request ID, keep Save As path changes tied to successful acknowledgement, and prevent edits during final close or refresh the close target afterward. Worker wake callbacks may request a repaint. File I/O can still block on the OS; a blocked filesystem operation also delays worker shutdown. This is not a cancellation or power-loss guarantee.

Checks cover real timers and file I/O, Save As ownership/failure, manual retention, automatic mode switching, immutable acknowledgements with editor Undo/Redo, discard, failed manual requests and bounded pending snapshots. The desktop integration also has tests for persisted settings, ordered acknowledgements, pending-action failures, legacy migration, active and archived recovery selection, external conflicts, explicit discard and close. Native platform acceptance remains separately recorded in the current checkpoint.

## Command-line startup opening

A project supplied at launch is prepared on a worker so named-file access does not hold the UI constructor. The window can show the file name, a waiting indicator and Cancel. Editing and unrelated document commands remain blocked until completion or cancellation; Close/Quit remains available. Escape cancels the pending load. Cancelling discards its result and does not join a blocked operating-system read. It cannot revoke an already issued OS access prompt or abort the underlying read; the candidate releases its working-copy lock when that read returns. It never applies a late result over subsequent work.

The worker reuses named-file/working-copy reconciliation and does not write the named file. UI completion validates page layout and then adopts the candidate. Missing/corrupt files or worker failure leave the existing document and recovery offers available. Conflicting earlier local work remains recoverable and is reported. Native first-launch/permission behavior is not yet accepted. Menu Open uses the separate preparation/handoff contract below. Local preference/legacy-recovery initialization still performs synchronous I/O; neither worker establishes that all I/O is nonblocking.

## Recovery discovery

Working-copy and archive discovery, including checks for missing named files, runs on a background worker. At most one discovery worker runs per app; repeated refresh requests coalesce into one fresh scan after the active scan completes. Superseded results are not applied, and the active document owner is filtered when fresh results arrive.

Recover work shows a scanning state and Later. Escape on the top picker has the same effect as Later; a popup or error above it owns the key first. Both leave eventual results available without reopening the picker. Document actions and command-line Open suppress automatic offers; an edited document, active gesture, text focus or modal also prevents a late automatic interruption. Both framework and custom text-entry focus count. Since discovery is polled before widgets, a first pointer press/held button, text, paste, composition, accessibility action, wheel or pressed key also prevents a completion from taking over that frame. Explicit Recover work remains available. Valid offers and per-record errors are retained together. The list and errors scroll above Later, including at minimum window size. Read failures never repair or remove recovery records.

A stalled OS read can keep the discovery worker waiting; it does not block the UI or require joining the worker on exit. Cached Restore actions remain disabled during a refresh so outdated choices are not presented as verified results. Completion requests a repaint; background waiting does not add a continuous repaint loop. Native permission/network-filesystem behavior remains separate acceptance work.

## Window close ordering

A window close is initially cancelled while the application retains its close request. Field input must reach the document before unsaved-state checks, and split input must drain across Save or clipboard completion before deciding to exit. The final UI step commits the editor and uses the same Quit/save/confirmation path as explicit commands. Cancelling that confirmation does not retain a hidden close request. A successful clean close is acknowledged so its subsequent native close event is allowed.

Logic-only close handling also cancels premature exit. A minimized window requests restoration so retained input and any confirmation can be processed in a UI pass. This is verified with actual application logic/UI callbacks and an empty framework test frame, not a native window or OS process-close test. Forced termination and blocked OS operations remain outside this proof. Native acceptance for the specific normal-window cases below is now recorded separately.

## Native close and dialog cancellation

The Close Review candidate verifies native macOS red-window-close delivery in two named cases: a canvas text draft with manual saving, and an active inspector text field with automatic saving. Manual close commits the draft before review; Escape cancels closing without losing the edit, and one Undo restores the exact baseline. Automatic close flushes the inspector edit without Return or an explicit Save. Both final files survive cold reopen byte-for-byte.

Escape is Cancel in unsaved review, never Discard. An error above that review owns the first Escape; a second Escape cancels the review. Native removal of only the disposable named destination produced a real save failure without closing or replacing the missing file. Independent dismissal retained the edit; restoring the fixture and retrying Save closed successfully. The original automatic-save preference was restored. Two new full-application regressions fail before the correction; all eight close tests and 414 application tests pass afterward, with one optional renderer ignored. Evidence: external release-closure/native-close-current/report.md.

This does not establish native IME composition, minimized-window delivery, every field/mode combination, OS permission behavior or paired reference equivalence. Startup cancellation cannot revoke an in-flight OS read; menu Open has the separate handoff boundary below. Keep those limits distinct from the accepted close sequences.

## Menu Open preparation and handoff

After the native chooser and existing unsaved-change decision, a worker resolves the destination's normalized working-copy identity and prepares its contents. The current editor, history and source session stay owned until preparation and page-layout validation succeed. Cancel releases an eventual prepared destination without changing the current document; edits and saves can resume through the existing source owner. Missing, corrupt or busy destinations leave the current work intact. Discard also validates the named file before relinquishing current local work, even if the destination has a recoverable copy.

A second worker observes the current document and finishes or explicitly discards its session. An already prepared different destination stays locked during this handoff. Same-file reopening, including normalized aliases, waits for source ownership to be released before opening that identity again. The final handoff is not cancellable; Close/Quit is queued until it settles. UI drawing remains available, but an operating-system read can delay this phase. If the source was explicitly discarded and the destination then fails, the visible document remains available and Save As creates a fresh recovery source instead of requiring the missing original file.

Nine application checks cover clean/manual/automatic paths, missing/corrupt/locked destinations, delayed cancellation and late ownership release, same-identity preservation/discard, symlinks, late failure with Save As and queued Quit. The full application suite passes 425 tests with one optional renderer ignored. Native macOS checks verify active inspector input with automatic Open, manual review/Cancel/exact Undo, Save-and-Open, invalid-file rejection, same-file reopen and byte-exact cold results. Evidence: external release-closure/menu-open-current/report.md. Native slow-file/permission prompts, Discard races and alias-chooser delivery remain unverified; Windows stays on hold. Startup preparation, recovery discovery and prior unchanged failure checks retain their scoped evidence.


The final Open Review 2 candidate also corrects raw editor shortcuts bypassing a standalone error or an Open started earlier in the same input batch. Both regressions fail before correction and pass afterward. Native Delete/Open/New remain blocked beneath an invalid-file error; Escape dismisses it, selection/history stay intact and Save retains byte-identical project data. This refreshes the affected modal/input evidence on the final candidate; the preceding native Open workflows retain their unchanged scope.
