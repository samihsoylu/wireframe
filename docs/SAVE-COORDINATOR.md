# Revision-aware save scheduling

The save coordinator establishes the ordering contract for automatic named-file saving. The desktop integrates this library component through `ProjectSession`, which owns per-project working copies and performs background I/O. The app submits document snapshots, consumes acknowledgements and retains its editor history. The former single recovery slot remains a migration and fallback path.

Each project session has three revisions: the current edited document, the last durable local checkpoint, and the last completed named-file write. New document changes, including Undo and Redo, advance the current revision. A successful local write acknowledges its own revision. New local revisions restart a five-second automatic-save delay; duplicate acknowledgements leave the deadline unchanged. A loaded project starts clean; a restored local edit is registered as a new edited revision and acknowledged locally.

A poll issues at most one write ticket. Its revision identifies an immutable document snapshot that the caller must retain. The caller writes that snapshot and reports the result with the same ticket. It must never substitute the mutable working file for an in-flight snapshot. Successful completion acknowledges exactly that revision, leaving newer edits dirty. Delayed completions from an earlier write or another project session are rejected without changing active work.

A failed write is retried once after one second, using the same snapshot and a new ticket. A second failure exposes the message and leaves work dirty; polling alone does not loop retries. An already scheduled future debounce for a newer edit still runs at its deadline; a deadline that elapsed during the failed write does not start another attempt. Explicit Save, re-enabling automatic saving, or a newer durable local checkpoint permits another attempt. A repeated acknowledgement of an unchanged checkpoint does not clear the error.

Explicit Save or automatic close captures a requested revision. Saving waits for that revision to be durable locally. If an older write is already active, its completion cannot fulfill the newer request; the next write starts as soon as the requested snapshot is available. The caller can proceed only when the named revision reaches the captured target. Close must stop edits or refresh its target after later edits. A request intentionally does not absorb edits made after it was issued.

Automatic saving is on by default. Turning it off cancels future automatic work, while explicit Save and already-started writes/retries continue. Turning it back on makes the currently durable local work immediately eligible. Manual application quit retains local edits; manual window close asks how to handle them. Those UI actions and local-copy retention are caller responsibilities, not implemented by this coordinator.

The clock uses monotonic elapsed durations supplied by the caller. `next_deadline` permits event-driven scheduling; completion or checkpoint events also require a poll. No background thread, filesystem dependency, wall clock, project parser or user-interface code lives in the coordinator. The storage boundary remains responsible for atomic writes and error reporting. Never acknowledge a failed local write or a failed named write as durable.

Seventeen controlled tests cover scheduling, immutable revision acknowledgements, flush requests, retries, mode changes, duplicate and foreign completions, invalid checkpoint ordering and counter limits. Two disk tests use the actual project codec and atomic writer to verify older named writes cannot erase newer local snapshots, and a failed destination retains local data before a successful retry.

Per-project identity and locks, checkpoint retention, persisted automatic-save preferences, external-change protection and UI status/error handling are integrated. See [project sessions](PROJECT-SESSION.md), [working copies](WORKING-COPIES.md) and [recovery](RECOVERY.md) for their implementation and verification boundaries. Coordinator tests prove ordering, not native platform behavior or crash/power-loss guarantees. Native restart, close and failure checks retain their recorded platform and candidate scope; Windows native testing remains on hold.

A caller can end a failed explicit flush request without cancelling an issued write. The background session uses this after reporting failure so later manual edits cannot revive that request. See docs/PROJECT-SESSION.md for the worker integration.
