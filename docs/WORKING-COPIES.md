# Per-project working copies

`WorkingCopies` is the durable storage boundary for the save coordinator. Each named project has a record identified by its canonical native path; each unnamed project gets its own reserved identifier. An OS file lock owns one record at a time. Multiple projects can coexist, and dropping ownership leaves their edits available for reopening. A random identifier collision is checked under the lock and never replaces earlier unnamed work. An acquired-lock guard explicitly unlocks when ownership ends, including temporary acquisition/error paths. Closing the file alone can leave its lock retained by a descriptor briefly inherited during process spawning. Live competing owners still return Busy; other OS locking errors retain their I/O error.

One atomically replaced JSON record contains the local document, saved-file identity, acknowledged file/content fingerprints and an optional pending-write fingerprint. Native path units are preserved without lossy Unicode conversion. Records are local application state, not a portable interchange format. Project serialization and validation remain unchanged.

A checkpoint changes only the local document. `save_named` accepts an immutable snapshot which may be older than that document. It checks the named file against the acknowledged SHA-256 fingerprint, writes a pending journal locally, checks the named file again, writes that snapshot atomically, then acknowledges its fingerprint in the record. It never substitutes the snapshot for newer local edits.

If a named write succeeds but acknowledgement fails, the pending fingerprint recognizes that write when reopening or retrying. Acknowledgement can then finish while retaining the latest local document. If the named write never happened, the old saved file and pending local work remain. A later external change is still a conflict. Scheduling and retry timing belong to the coordinator; the storage layer returns errors to its caller.

Dirty state compares canonical project content against the last acknowledged named content, separately from the exact file-byte fingerprint. Formatting differences in a loaded file do not create false edits. Older-save completion cannot clear newer local edits. Unnamed work remains locally unsaved until the caller assigns a named destination or explicitly discards it.

A valid local record can reopen when its named file is missing, unreadable or externally changed. The caller receives the named-file status and can select the appropriate candidate. Changed files are decoded for that decision but are not overwritten automatically. Missing files are not silently recreated by `save_named`. Save As reserves a selected destination through `prepare_save_as` before a named write. The source owner must be retained until the returned destination has saved successfully. Explicit same-path Save As refreshes its captured baseline; ordinary writes retain their guard. Opening a changed named file retains different local edits as a separately recoverable unnamed copy before loading the named version.

Unreadable local records are visible in listing results. When a valid named file can be opened, an invalid local record is first moved to a unique archive and its original bytes are preserved; the returned copy exposes that location. Unsupported future record versions are left untouched and return an error. If neither candidate can be decoded, both remain intact. Non-regular local paths are not replaced during fallback. File reads are bounded, and decoded projects are validated before use.

Explicit discard removes only the selected local record. Its stable lock file remains, preventing competing processes from locking different inodes during close. Named files and other projects are retained. Archives and lock files are excluded from the active working-copy list.

Focused tests cover independent projects, ownership and aliases, reopen, dirty content, older saves, external changes, missing/unreadable files, preserved fallback, future formats, checkpoint/write/acknowledgement failures, identifier validation and collisions, explicit discard, native path encoding, non-regular paths, destination reservations, competing Save As owners, migrations and required fingerprint fields. A worker-thread integration test connects the coordinator to real working-copy writes and verifies immutable snapshots, flush targets, ownership and reopening. The two coordinator disk tests remain separate from worker and desktop coverage.

Limits: checks immediately before atomic replacement detect ordinary external changes but cannot prevent an unrelated process from writing between the final check and replacement. Locks coordinate users of the same working-copy store; they do not lock out every external editor. Filesystem-specific aliases, hard links and inaccessible/missing parent paths can need further identity handling. Non-Unicode path units round-trip in metadata; actual filesystem acceptance varies. The storage tests passed on macOS and Linux, including three parent tests that kill real child processes across five save boundaries, three external-change cases and 24 Save As combinations. They verify OS lock release, the last completed checkpoint, journal reconciliation, guarded retry, source retention and immutable recovery of previous destination edits. The helper is intentionally ignored in the ordinary test listing and invoked explicitly by its parent tests. Native macOS crash cases and a current Linux full-app completed manual-checkpoint case now have separate scoped evidence; other Linux mode/destination/interleaving cases, Windows, power loss and termination inside an atomic write remain unverified. See [recovery](RECOVERY.md) for actual full-app scope and the Save As matrix's worker boundary.

Current native macOS Save As also verifies live destination-lock rejection, unchanged source/destination files, retained source recovery/association and exact saved history. Releasing the separate test-process owner permits retry/adoption, and a subsequent Save changes only the adopted destination. External `appearance-finishing-current/delivery/save-as-owner` retains exact current-package identity, native/file/lock observations and 546-file/preference restoration. It does not establish every native race/permission/mode or a second GUI-app workflow.

The desktop uses these copies through the background session; see docs/PROJECT-SESSION.md and docs/SAVING.md. File → Recover work lists changed active copies and valid previous-copy archives. Archive restoration validates the stored project and creates a new unnamed owner, keeping the original archive and ignoring its former named-file association. Invalid, future-version and non-regular archive entries remain intact and are reported. Native acceptance is recorded separately in the current checkpoint.

## Project schema migration

Record format2 stores the current project schema. The reader also accepts format1 records and migrates their embedded documents through the ordinary document decoder. Reading a clean or edited record does not rewrite it or its named project. Old canonical content fingerprints are translated only when they prove the prior record was clean; unsaved edits remain marked as local changes. Interrupted-save reconciliation retains the raw-file fingerprint for external-write checks and derives the content baseline from the migrated saved project. Recovery archives migrate into a separate unnamed copy, preserving the archive bytes. Future record or embedded-document versions remain unsupported and are left intact.

Embedded project version5 retains complete trashed pages. Recovery recognizes clean version3/4 canonical baselines without rewriting old records on read, while unsaved changes remain dirty. Retained pages and their alternate notes/parent references survive checkpoint, process-owner release, resume and named save.

Embedded version6 documents preserve component libraries, source placements and separate notes. Recovery recognizes clean version3–5 canonical baselines before applying schema migration, including files with component definitions. Unsaved copies remain dirty. Reading an old recovery record or named project does not rewrite either file.

## Descriptor lifetime

The working-copy and legacy recovery paths use the same acquired-lock guard. Deterministic tests retain a duplicate descriptor, verify that a live owner excludes a contender, drop the owner and reacquire before closing the duplicate. Closing that old duplicate must not release the successor's separate lock. A macOS concurrent-spawn reproducer confirms the close-only failure and the explicit-unlock correction. Crash tests still validate OS cleanup when destructors cannot run; a surviving inherited descriptor can extend a crashed owner's lock until that descriptor closes. No retry or timeout weakens ownership, and no lock file is removed.
